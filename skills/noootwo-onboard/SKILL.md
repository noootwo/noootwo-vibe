# Noootwo Onboard

Enter a project you do not know and leave with the smallest decisions that make work safe: which skills govern it, which parts of the foundation are missing, and what to fix first. Context lifecycle `write -> select -> compress -> isolate -> verify`: load this skill and triggered reference sections; route references over 200 lines through headings or query hits; cap live excerpts at 80 lines; put output over 16 KiB in cold evidence with path and hash; isolate only independent read-only work; keep one writer; verify summaries against source.

This is not a code review and not a product interview. It produces a routing map and a gap list, not a scaffold.

## 1. Read the nearest evidence

- `AGENTS.md`, README, `docs/status.md`, ADRs, release notes.
- Package and build files, CI workflows, scripts, test commands.
- The changed files or the request text, and recent git history.

Never load every skill. Load a skill body only after a project fact makes it relevant.

**Done when:** you can name the project type, the stack, the validation entry, and what is still unknown.

## 2. Audit context health

Use file size, headings, hashes, and query hits before reading. Name any entrypoint that forces a whole read, an on-demand file above about 200 lines without a section route, a stale noootwo-docs or noootwo-review reference, a status file that became a timeline, or a missing path for short-term state and evidence.

When a gap is real, invoke `noootwo-state` and add the smallest AGENTS, status, or state adapter: bounded re-entry, one writer, and links to existing history. Preserve every historical file; do not auto-move, merge, rewrite, or delete it.

**Done when:** each context finding has evidence, and any patch is the smallest adapter that restores bounded reading.

## 3. Audit the skill set

Read `references/skill-audit.md` for the decision table and the output contract. Every required skill carries the trigger that fires it; every optional local skill carries the condition that loads it; every skill left out carries a reason.

**Done when:** each skill is required, optional with a trigger, or explicitly not needed now.

## 4. Route the health judgment

The foundation itself — validation entry, tests, CI, decisions, runtime preview, context cost, risk log — is judged by the `noootwo-code-health` skill's project-health lens. Release path, version sources, artifact identity, deployment trace, and rollback readiness are judged by `noootwo-release`. Invoke the owning skill: read its `SKILL.md` and follow it, and hand over the repo facts already read rather than re-reading them.

Do not classify foundation health here. One surface, one owner.

**Done when:** the health findings are recorded with their evidence, or the reviewer states nothing needs fixing now.

## 5. Patch the smallest thing

Read `references/foundation-templates.md` only after a real gap exists, and add the single missing file or section that unblocks the work in front of you.

**Done when:** every added file traces to a named gap, and nothing was generated by default.

## 6. Hand off

Report the project type, context-health findings, the required skills with their triggers, the optional local skills, the not-needed list, the foundation gaps with their owners, and the patch applied or proposed. When facts about the project changed, invoke the `noootwo-state` skill to place them. When the next step is a real product, design, or code decision, invoke the skill that owns it.

**Done when:** the map and the gaps are delivered, and every change is placed by its owning skill.

## Return

When the request is not onboarding — one bug, one feature, one review — say so in one line and route in one hop instead of auditing the project.

## Reference

- `references/skill-audit.md` — the skill decision table, the local skill scan, and the audit output contract.
- `references/foundation-templates.md` — the smallest foundation files, used only after a named gap.

Missing skill fallback: first try `npx -y skills add noootwo/noootwo-vibe --global --agent codex --skill <name> --yes`; if install fails, take the smallest direct fallback and mark the record `skill-missing: <name>` (for persistence, write the owning file directly).
